## STEP 1 — Observation (관찰)

### 1. 현재 우리가 해결하려는 상황은 무엇인가?

**관찰된 상황:**  
4×4 격자에 1부터 16까지의 정수를 각 칸에 **한 번씩** 배치했을 때, 행·열·대각선(또는 특정 선 집합)의 합이 **모두 동일한 값**을 갖도록 하는 배치가 존재하는지, 그리고 그런 배치를 **어떻게 찾거나 생성·검증할 수 있는지**를 다루는 상황이다.

더 넓게 보면:

- **입력:** 크기(4×4), 사용할 수의 범위(예: 1~16), “같아야 하는 선”의 정의(일반 마방진 vs. 반마방진 등)
- **출력:** 조건을 만족하는 격자, 또는 “존재하지 않음 / 여러 개 존재”에 대한 설명
- **불확실성:** “마방진”이라는 말만으로는 **어떤 선까지 합이 같아야 하는지**, **해가 유일한지**, **사람이 직접 채울지 프로그램이 자동으로 채울지**가 아직 정해지지 않은 상태

즉, “만들기”가 아니라 **「4×4에서 정해진 규칙을 만족하는 숫자 배치」라는 제약 충족 문제**가 놓여 있는 상황으로 볼 수 있다.

### 2. 왜 4×4 마방진 문제를 다루는가?

**관찰된 동기(가능한 이유들):**

| 관점 | 관찰 |
|------|------|
| **규모** | 3×3보다 제약이 많고 패턴이 덜 직관적이며, 5×5 이상보다는 탐색·표현·검증이 다루기 쉬움 |
| **수학·퍼즐** | 고전 퍼즐·조합 문제로, “합이 같다”는 단일 불변량(invariant)이 명확함 |
| **프로그래밍 학습** | 2차원 배열, 반복·조건, 백트래킹/휴리스틱, 검증 로직 등을 **작은 단위**로 연습하기 좋음 |
| **시스템 설계 입문** | “생성 / 검증 / 표시”처럼 역할을 나누기 쉬운 최소 기능 단위 |
| **프로젝트 이름** | `MagicSquare_XX`의 `XX`는 **4×4에 고정**하거나, 이후 다른 크기로 확장할 여지를 남긴 명명일 수 있음 |

**아직 확인되지 않은 점:**  
“4×4를 선택한 이유”가 **교육용·과제·취미·알고리즘 실험** 중 무엇인지는 저장소에 기록이 없어, 위는 **가능한 동기의 관찰**이다.

### 3. 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

#### 학습 맥락

- **기초 프로그래밍:** 2D 배열, 루프, 함수 분리, 입출력
- **알고리즘:** 제약 만족, 백트래킹, 완전 탐색 vs. 알려진 구성법(Siamese 등 — 4×4는 홀수 전용법과 다름)
- **수학적 사고:** 마법 상수 \(M = n(n^2+1)/2\) (4×4이면 34), 대칭·패턴, 해의 개수·동형(회전·대칭)

#### 시스템 설계 맥락

- **도메인 모델:** 격자(Grid), 셀(Cell), 선(Line: 행/열/대각), 규칙(Rule), 해(Solution)
- **책임 분리:** 규칙 정의 · 배치 생성 또는 탐색 · 합·유일성 검증 · 사용자에게 보여 주기
- **품질:** 잘못된 입력, 부분 채움, “거의 맞는” 격자에 대한 피드백 등 **검증 계층**을 어디에 둘지

#### 이 문제가 특히 드러내는 설계 이슈

1. **“마방진” 정의가 구현보다 먼저** — 반마방진, panmagic, 일반 마방진 등 정의에 따라 검증·생성 난이도가 달라짐
2. **생성 vs. 검증** — 사용자가 채우는 퍼즐인지, 프로그램이 하나를 제시하는지에 따라 아키텍처가 달라짐
3. **4×4의 특수성** — 짝수 차수 마방진은 홀수 차수와 다른 구성·이론이 있어, “일반 n×n”으로 바로 일반화하기 어렵다는 점

### 관찰 관점 요약 (한 문장)

> **「16개의 서로 다른 정수를 4×4 격자에 놓았을 때, 정해진 여러 ‘선’ 위 숫자의 합이 모두 같아지는 배치가 있는지, 그리고 그 배치를 사람·프로그램이 어떻게 다룰지」**를 아직 요구사항 없이 맞닥뜨린 초기 상황이다.

## STEP 2 — Why #1

### 질문

**Q: 왜 마방진을 완성해야 하는가?**

### 가정한 답 (A)

> **A:** 4×4 격자에 1~16을 한 번씩 배치했을 때, **모든 행·열·대각선의 합이 34로 같아지는지**를 프로그램으로 **확인하고**, 맞지 않으면 **어디가 어긋났는지 알려 주기 위해** 마방진을 “완성”(또는 완성 여부를 판정)해야 한다.

즉, 목적은 **퍼즐/연습 문제의 정답 검증**이며, “예쁜 마방진 하나를 자동 생성”하는 것은 1차 목적이 아니다.

### A에서 드러나는 불편함 · 구조적 문제

#### 1. “완성”의 의미가 모호함

| 관찰 | 구조적 문제 |
|------|-------------|
| 사용자는 “16칸을 다 채웠다”고 느끼지만, 프로그램은 “합이 맞는 완전한 해”만 인정할 수 있음 | **완성**이 *채움 완료*인지 *규칙 만족*인지 정의가 갈라지면, UX·메시지·상태 모델이 어긋남 |
| 일부 행만 맞고 대각은 틀린 “반쯤 맞는” 격자가 흔함 | 이진 판정(성공/실패)만 있으면 **학습자에게 피드백이 거칠어짐** |

**불편함:** “왜 아직 완성이 아니냐”에 대한 답이 **어느 선·어느 칸**인지 없으면, 사용자는 다시 전체를 눈으로 훑어야 한다.

#### 2. 검증만을 목적으로 할 때도 “생성” 압력이 생김

| 관찰 | 구조적 문제 |
|------|-------------|
| 연습용으로 **정답 예시**나 **빈 칸 퍼즐**이 필요해짐 | 검증 시스템만 만들려 해도, 곧 **해 생성·샘플 제공** 요구가 붙음 |
| 4×4 마방진 해는 여러 개(대칭 동형 포함) | “정답이 하나”라고 가정하면 **동일 합·다른 배치**를 오답 처리할 위험 |

**불편함:** Why가 “검증”인데, 설계 범위는 자연스럽게 **생성·채점·힌트**까지 넓어진다. **단일 목적(A)과 실제 필요 기능의 불일치**가 초기에 숨어 있다.

#### 3. “모든 선의 합 = 34”는 사람에게는 계산 부담

| 관찰 | 구조적 문제 |
|------|-------------|
| 사람은 행 몇 개만 더해보고 “됐다”고 착각하기 쉬움 | 프로그램의 **완전 검증**과 사람의 **부분 확인** 사이에 인지 격차 |
| 4×4는 선이 10개(행4+열4+대각2) | 어떤 선을 먼저 보여줄지, **실패 우선순위**를 정하지 않으면 피드백이 임의적임 |

#### 4. 입력 모델이 정해지지 않으면 검증 자체가 불안정

| 관찰 | 구조적 문제 |
|------|-------------|
| 빈 칸, 중복 숫자, 1~16 밖의 값, 미입력 | “합 검증” 전에 **전제 조건 검증** 레이어가 필요 |
| 사용자가 칸을 하나씩 채우는 중간 상태 | **완성 전**에도 검증을 호출할지, 막을지 정책이 필요 |

#### 5. 4×4라는 크기가 Why를 키우지는 않지만, 착각을 유발함

| 관찰 | 구조적 문제 |
|------|-------------|
| 3×3은 손으로도 익숙하고 해가 적음 | “검증만 하면 쉬울 것”이라는 **과소평가** |
| 4×4는 짝수 차수라 구성법이 홀수와 다름 | 나중에 “n×n으로 확장”하려 하면 **Why #1(검증)과 알고리즘 계층**이 엇갈림 |

#### 6. A가 숨기는 “진짜 불편” — 신뢰 문제

> **「내가 맞다고 생각하는 배치를, 기준 없이는 확신할 수 없다.»**

| 구조적 문제 | 설명 |
|-------------|------|
| **권위의 출처** | “34”가 맞는지, 선 정의가 맞는지를 누가 정의하는가 (교재? 프로그램?) |
| **설명 가능성** | 틀렸을 때 “34가 아님”만으로는 **왜 그 선을 봐야 하는지** 교육 목적이 충족되지 않을 수 있음 |
| **책임 경계** | 오류가 사용자 입력인지, 규칙 정의인지, 구현 버그인지 구분되지 않으면 신뢰가 깨짐 |

### Why #1 분석 요약

1. **완성**은 “16칸 채움”이 아니라 **규칙 만족**이며, 그 전에 **유효 입력** 문제가 선행된다.
2. 검증만이 목적이어도 **피드백·예시·부분 상태** 요구가 따라와 **범위 팽창**이 일어난다.
3. 4×4는 해가 여러 개라 **단일 정답 비교** 모델은 구조적으로 위험하다.
4. 표면적 Why(검증) 아래에는 **기준 정의·설명·신뢰** 문제가 있다.

### 핵심 긴장 (한 줄)

> **「완성해야 한다」는 요구는 검증 시스템처럼 보이지만, 실제로는 *규칙 정의 + 상태 관리 + 설명 가능한 피드백*까지 요구하는 복합 문제다.**

## STEP 3 — Why #2

### 질문

**Q: 왜 단순 계산이 아니라 프로그램으로 구현하는가?**

STEP 2에서 가정한 맥락: **4×4 격자, 1~16, 행·열·대각 합 34, 정답·오류 판정과 피드백**이 필요한 상황.

### 1. 반복 가능성 (Repeatability)

**관찰:** 손계산·종이 검산은 **한 번의 격자·한 명의 판정**에는 충분할 수 있지만, 같은 절차를 **여러 번·여러 입력·여러 사람**에게 동일하게 적용하기 어렵다. 프로그램은 **동일한 규칙을 동일한 순서로** 반복 실행할 수 있다.

**구조적 문제:**

| 문제 | 설명 |
|------|------|
| **반복 ≠ 가치** | 시도 횟수가 1~2회면 프로그램 유지 비용이 손계산보다 클 수 있음 |
| **환경 의존** | 실행 환경이 바뀌면 “반복 가능”이 **재현 가능한 개발·실행** 문제로 확장됨 |
| **입력 형식** | 격자 입력 방식이 정해지지 않으면, 반복은 **도구 반복**이지 **사용 반복**이 아님 |

### 2. 검증 자동화 (Verification Automation)

**관찰:** 확인할 선은 **행 4 + 열 4 + 대각 2 = 10개**이다. 프로그램은 **정의된 모든 선**을 빠짐없이 검사하고, 실패 시 **어느 선·어느 합**인지를 기계적으로 보고할 수 있다.

**구조적 문제:**

| 문제 | 설명 |
|------|------|
| **자동화 대상의 모호성** | “합 검증”만 자동화할지, **1~16 중복·범위·빈 칸**까지 자동화할지 범위가 불명확 |
| **부분 완성** | 16칸 미만일 때 자동 검증을 허용할지 정책이 필요 |
| **피드백 설계** | 자동화는 *판정*까지 쉽고, *교육적으로 유용한 설명*은 별도 요구사항 |
| **다중 해** | “정답 일치 비교” 자동화와 “규칙 만족” 자동화는 **다른 기능** |

### 3. 오류 방지 (Error Prevention)

**관찰:** 손계산 오류(덧셈 실수, 중복, 범위 위반, 칸 누락)와 검산자의 **2차 오류**를 줄일 수 있다.

**구조적 문제:**

| 문제 | 설명 |
|------|------|
| **오류 이동** | 사람의 덧셈 오류 대신 **잘못된 규칙 정의**가 새 단일 실패점이 됨 |
| **과신** | “프로그램이 맞다고 했으니 끝” → **권위 오류** 발생 |
| **입력 오류** | 잘못된 입력을 “정확히 잘못 검증”함 → **입력 검증**과 **마방진 검증** 분리 필요 |

### 4. 규칙 기반 사고 훈련 (Rule-based Thinking Training)

**관찰:** 마방진은 **명시적 규칙**의 교집합이다. 프로그램으로 구현하면 “무엇이 충족되면 통과인가”를 **실행 가능한 형태**로 고정하게 된다.

**구조적 문제:**

| 문제 | 설명 |
|------|------|
| **규칙 vs. 구현 혼동** | 훈련 목표가 **문법·도구 연습**으로 새어 나갈 수 있음 |
| **과도한 일반화** | 4×4 규칙 이해 전에 **추상화 부담** |
| **검증만 vs. 생성** | 규칙 기반 사고는 **생성(탐색)** 쪽이 더 강한데, Why #1이 검증이면 학습 목표와 **기능 범위**가 어긋날 수 있음 |

### 종합 답 (A)

> **단순 계산**은 한두 번의 합 맞추기에는 적합하지만, **같은 기준으로 여러 격자를 반복 검사**하고, **10개 선을 빠짐없이 판정**하며, **사람·검산자의 2차 실수**를 줄이고, **“통과 조건”을 명시적·실행 가능한 규칙**으로 고정하려면 프로그램이 합리적이다.

### Why #1 × Why #2 연결

```
[사용자 격자] → [입력 유효성] → [선별 합 계산] → [34와 비교] → [판정 + (선택) 피드백]
```

**숨은 전제:** 프로그램은 **계산 속도**보다 **판정의 일관성·완전성·재현성**을 제공하기 위해 도입된다.

### Why #2 한 줄 요약

> 프로그램은 **더 빠른 계산기**가 아니라, **같은 규칙으로 무한히·완전히·재현 가능하게 “완성 여부”를 판정하는 장치**이며, 그 과정 자체가 **규칙을 실행 가능한 형태로 고정하는 훈련**이 된다.

---

## STEP 4 — Why #3 (핵심 발견)

### 질문

**Q: 왜 이 문제를 TDD 방식으로 설계하려 하는가?**

### 핵심 발견 (한 줄)

> 마방진 문제는 **겉보기 단순한 산술**이지만, 실제로는 **규칙 정의·상태·판정 경계**가 어긋나기 쉬운 문제다. TDD는 **“무엇이 맞다/틀리다”를 구현보다 먼저 계약(테스트)으로 고정**해, STEP 2의 모호함을 **통제 가능한 명세**로 바꾸기 위한 수단이다.

### 1. 무엇이 통제되어야 하는가?

| 통제 영역 | 통제하지 않으면 생기는 일 |
|-----------|---------------------------|
| **규칙 정의** | “마방진”마다 요구 선·마법 상수가 달라짐 |
| **판정 경계** | 16칸 미만·빈 칸 처리가 흔들림 |
| **숫자 집합 제약** | 합만 맞고 1~16 밖·중복인 “가짜 해” 통과 |
| **검증 완전성** | 행만 보고 통과, 대각 누락 |
| **피드백 정책** | 같은 오류도 실행마다 다른 메시지 |
| **구현 신뢰** | “프로그램이 맞다”는 과신 |
| **범위 팽창** | 검증만 하려다 생성·UI까지 무계획 확장 |

**통제의 1순위:** **34를 빨리 계산**이 아니라, **어떤 전제가 깨졌을 때 무엇을 ‘틀림’이라 부를지**.

### 2. 어떤 불변 조건이 존재하는가?

#### (A) 도메인 불변

| 불변 | 내용 (4×4, 1~16) |
|------|------------------|
| **마법 상수** | 모든 검사 대상 선의 합 = **34** |
| **숫자 집합** | 격자 원소는 **{1,…,16}의 순열** |
| **선 집합** | 합을 맞춰야 하는 선 집합이 **정의와 일치** |
| **크기** | 항상 **4×4** |

#### (B) 판정 불변

| 불변 | 의미 |
|------|------|
| **완전성** | 정의된 모든 선을 검사하지 않고는 통과 판정 금지 |
| **단조적 거부** | 1~16 위반 → “합만 틀림”보다 **우선 거부** |
| **결정성** | 같은 격자 → 같은 결과 |
| **다중 해** | 배치가 달라도 규칙 만족이면 **동등 통과** |

#### (C) 부분 상태 불변

“마방진 불변(합=34)”과 “프로그램 불변(부분 입력 시 행동)”은 **다른 층**이다.

### 3. 왜 입력/출력이 명확해야 하는가?

| 명확해야 하는 것 | 이유 |
|------------------|------|
| **입력: 격자 표현** | 형식마다 fixture가 재사용 불가 |
| **입력: 빈 칸·잘못된 값** | 거부 vs 오류 vs 무시가 테스트마다 달라짐 |
| **출력: 판정 타입** | 피드백 요구와 테스트 기대값이 연결됨 |
| **출력: 실패 이유** | 어떤 불변을 깨었는지 회귀 시 추적 불가 |
| **출력: 순서·안정성** | 동일 입력에 동일 출력(결정성) 필요 |

**발견:** 핵심 출력은 종종 **“34”**가 아니라 **판정 결과(통과/거부/미완성 + 이유)**이다.

### Why #3 종합

| 질문 | 답 |
|------|-----|
| 왜 TDD인가? | 산술이 아니라 **판정 계약**이 핵심 |
| 무엇을 통제? | 규칙 정의, 검증 완전성, 부분/완성 경계, 피드백, 회귀 |
| 불변은? | 합=34, 1~16 순열, 선 집합, 결정성, 부분 상태 처리 |
| I/O는? | 테스트가 **재현 가능한 사양**이 되도록 입출력을 먼저 고정 |

## STEP 5 — 진짜 문제 정의

### 1. 표면 문제 정의 (잘못된 정의)

> **「4×4 마방진을 만드는 프로그램을 만든다.」**

| 한계 | 설명 |
|------|------|
| **목표가 행위에 고정됨** | 생성·완성·표시·검증이 한 덩어리 |
| **“마방진”이 비어 있음** | 선·숫자 집합·부분 채움 미정 |
| **완성의 의미가 혼재됨** | 16칸 채움 ≠ 규칙 만족 |
| **사용자·맥락이 없음** | 반복·신뢰·피드백 요구 누락 |
| **훈련 목표가 숨김** | 규칙을 명시하고 판정하는 사고가 빠짐 |

### 2. 개선된 문제 정의 (정확한 정의)

> **「4×4 격자에 놓인 1부터 16까지의 숫자 배치가, 미리 합의한 선(행·열·대각) 집합에 대해 모두 동일한 합(34)을 만족하는지, 그리고 숫자 집합 제약(각 수 한 번, 범위 내)을 만족하는지를, 동일한 기준으로 반복·완전·재현 가능하게 판정하고, 만족하지 않을 때는 어떤 조건이 깨졌는지 구분해 알려 줄 수 있어야 한다.」**

#### 정의에 포함된 요소

| 요소 | 내용 |
|------|------|
| **대상** | 4×4 격자 위의 숫자 배치 |
| **전제** | 1~16, 각각 정확히 한 번 |
| **규칙** | 합의된 선마다 합이 34 |
| **행위** | 주어진 배치에 대해 **판정** (필요 시 구분된 피드백) |
| **품질** | 같은 입력에 같은 결론, 선 검사 누락 없음 |
| **경계** | 미완성은 완성 판정과 **별도** |
| **다중 해** | 특정 한 배치와의 일치가 성공 조건이 아님 |

#### 비목표

- 임의 크기 격자로의 일반화
- “정답 하나”와의 위치적 일치
- 탐색 성능·최적화
- 시각적 연출·게임성 자체

### 3. 이 문제의 핵심 Invariant

#### (A) 대상(마방진)에 대한 불변

| ID | 불변 조건 |
|----|-----------|
| **I-1** | 격자는 항상 4×4이다. |
| **I-2** | 칸에 들어 있는 수는 1~16이며, 16개 수는 서로 다르다. |
| **I-3** | 합의된 모든 선(행 4, 열 4, 대각 2) 위 숫자의 합은 **34**이다. |
| **I-4** | 조건을 만족하는 배치가 여러 개일 수 있으나, **어느 하나도 다른 하나보다 “더 정답”이 아니다**. |

#### (B) 판정(검증 행위)에 대한 불변

| ID | 불변 조건 |
|----|-----------|
| **V-1** | 정의된 선·숫자 집합 검사를 **모두 수행하기 전에는** “규칙 만족”으로 판정하지 않는다. |
| **V-2** | 숫자 집합·범위·중복 위반은 합이 맞더라도 **우선하여 거부**한다. |
| **V-3** | 동일한 배치에 대해 판정 결과는 **항상 동일**하다. |
| **V-4** | “16칸 채웠으나 규칙 불만족”과 “판정 정보 부족”은 **서로 다른 결과**이다. |

#### (C) 메타 불변

| ID | 불변 조건 |
|----|-----------|
| **M-1** | “마방진”의 의미는 **판정 전에 고정**되어 있으며, 이해관계자가 공유한다. |
| **M-2** | 성공은 **특정 예시 배치와의 일치**가 아니라 **고정된 규칙 집합의 충족**이다. |

### 4. 우리가 실제로 훈련하려는 사고 능력

| 능력 | 설명 |
|------|------|
| **규칙 명시화** | “마방진”, “완성”을 검사 가능한 조건으로 분해 |
| **경계·상태 구분** | 미완성 / 유효하지 않은 입력 / 규칙 불만족 / 규칙 만족 구분 |
| **완전성·일관성** | 조건 목록을 빠짐없이, 매번 같은 기준으로 적용 |
| **불변 중심 사고** | 합 34, 숫자 집합, 선 집합을 먼저 고정; 반례로 깨진 불변 짚기 |
| **계약·입출력 사고** | 판정 전에 입출력 합의; 실패 유형 구분 전달 |
| **검증 가능한 주장** | “잘 동작한다”를 구체적 사례로 바꿔 말하기 |

**훈련 목표 한 줄:**

> **산술을 빨리 하는 것이 아니라, “무엇이 참이어야 하는가”를 고정하고, 그에 대해 일관되게 판단·설명하는 사고를 훈련한다.**
